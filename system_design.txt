1. INTRODUCTION

1.1. Project Overview
AgriConnect is a full-stack agri-supply chain platform that connects farmers, suppliers and customers. 
It digitizes procurement, transparent bidding, quality verification, inventory, and B2C marketplace sales. 
Built as a modular monolith (Node.js + Express + TypeScript backend, React + Vite + Tailwind frontend) with 
PostgreSQL (source of truth), MongoDB (flexible/audit), Redis (cache) and real-time updates via Socket.IO.

1.2. Problem Statement
Traditional agri-supply chains suffer from: lack of price transparency, middlemen, poor traceability, 
delayed payments, quality disputes, and inefficient inventory matching between farm produce and buyer demand.

1.3. Proposed Solution
Provide a role-based platform where:
- Suppliers post procurement requests with quantity/grade/deadline
- Farmers bid transparently with price, qty, grade, delivery date
- Smart allocation recommends bids (recommendation only; supplier decides)
- Quality verification drives inventory ownership transfer
- Verified inventory becomes B2C product listings for customers
- Secure payments (Razorpay) with webhooks and idempotency

1.4. Goals and Objectives
- Transparency in bidding and allocation
- Fair matching via explainable scoring
- Traceable ownership (farmer -> verified inventory -> sale)
- Reliable payments and auditability
- Low-latency UX with real-time updates

1.5. Scope and Assumptions
Scope: FARMER, SUPPLIER, CUSTOMER roles; bidding, contracts, quality, inventory, products, cart/orders/payments, tracking, notifications, market prices.
Assumptions: test Razorpay keys in dev, images on Cloudinary, DBs reachable locally/Docker. 
Out-of-scope (MVP): admin panel, multi-supplier cart, GPS live tracking, AI auto-grading, advanced analytics.

2. REQUIREMENTS

2.1. Functional Requirements
- Auth (register/login/me, JWT, role-based)
- Supplier: create/close/cancel procurements, view bids, accept bids, manage contracts/inventory/products/deliveries
- Farmer: browse procurements, bid/update/withdraw (before deadline), view contracts, deliveries
- Customer: browse listings, cart, checkout, orders, tracking
- Quality verification, ownership transfer to inventory
- Payments: create order, verify, webhook
- Notifications, market prices (cached), real-time bidding updates

2.2. Non-Functional Requirements
- Consistency: critical writes in transactions (Prisma)
- Idempotency: payment webhooks
- Security: bcrypt + JWT, helmet, CORS, rate limiting, input validation (Zod)
- Performance: API < ~200ms typical; cache market prices
- Reliability: graceful error handling, source-of-truth in Postgres
- Observability: morgan (dev), structured errors
- Extensibility: modular monolith

2.3. User Roles
FARMER   |   SUPPLIER   |   CUSTOMER (exactly 3)

2.4. Constraints & Out-of-Scope
Constraints: Node v22, TS strict, single API origin in dev. 
Out-of-scope: admin role, microservices now, multi-tenant, live GPS.

4. HIGH-LEVEL ARCHITECTURE

4.1. Style
Modular monolith: feature modules (auth/procurement/bidding/quality/orders/payments). Clear boundaries, easy to extract later.

4.2. Components
- Client (React + Vite + Tailwind)
- API (Express + TS) behind /api/v1
- Postgres + Prisma (OLTP source of truth)
- MongoDB + Mongoose (audit/events/snapshots/chat)
- Redis (ioredis) cache + rate-limit counters
- Socket.IO (real-time)

4.3. Protocols
HTTP/REST + JSON, WebSocket (Socket.IO), HTTPS in prod.

4.4. Rationale
Fits current scope, type-safe, transactional correctness, low ops. Can evolve to event-driven/microservices later.

5. CORE WORKFLOWS

5.1. Auth: register/login -> JWT -> role-gated routes
5.2. Supplier creates procurement (OPEN) -> farmers notified
5.3. Farmer bids until bidDeadline (open visibility) -> validate grade/qty/deadline
5.4. Supplier closes -> smart ranking (recommendation only) -> accepts bids -> FarmerContract(s) created (transactional)
5.5. Delivery/receive -> quality verify (ACCEPTED/ADJUSTED/REJECTED/DISPUTED). ACCEPTED/ADJUSTED -> inventory (ownership transfer). REJECTED -> farmer, reliability adjusted. FAILED -> return undelivered qty, reopen bidding for remaining.
5.6. Supplier lists inventory as ProductListing -> customer browses/Cart
5.7. Checkout -> create order (PAYMENT_PENDING), reserve inventory atomically -> Razorpay order
5.8. Payment: webhook CAPTURED (signed, idempotent) -> order CONFIRMED, decrement stock
5.9. Tracking: supplier advances order status; events persisted; notifications + Socket.IO

7. DATABASE DESIGN

7.1. ERD Summary (Postgres)
Entities: User, FarmerProfile, SupplierProfile, CustomerProfile, Product, ProcurementRequest, Bid, FarmerContract, QualityVerification, InventoryItem, ProductListing, Cart/CartItem, Address, CustomerOrder/OrderItem, Payment, Delivery, Notification, Rating, AllocationWeight, BidImage.
Enums: UserRole, ProcurementStatus, BidStatus, ContractStatus, VerificationOutcome, OrderStatus, PaymentStatus, DeliveryStatus, TransportMode, AllocationMode, Grade, Unit, PaymentMethod.

7.2. Relationships
1:N and M:N via join tables where appropriate. Contracts 1:1 to verification. Orders -> items. Listings -> inventory source.

7.3. MongoDB Models
- AiAnalysis (kind/refId/input/output/model/confidence)
- ActivityEvent (actorId/role/type/entityType/entityId/data)
- NotificationPayload (durable log)
- ChatSession (userId/messages[])
- AllocationSnapshot (procurementId/weights/rankedBids/recommendedBids)

7.4. Redis
Cache-aside for market prices (key by crop/date range). Also rate-limit counters. TTL configurable.

7.5. Indexing/Constraints
FKs + unique where logical (emails unique). Composite indexes on frequent filters (status+dates). Soft-delete not heavy; status enums drive flows.

8. DETAILED COMPONENT DESIGN

8.1. Auth + RBAC: JWT verify, role guard
8.2. Procurement/Bidding: deadline checks, grade constraints, open visibility
8.3. Smart Allocation: weighted scoring (price 30%, quality 25%, qty 15%, delivery 10%, distance 10%, reliability 10%). Normalize, compute 0�1, weighted sum. Recommendation only.
8.4. Quality: receive -> verify -> ownership: ACCEPTED/ADJUSTED moves qty to supplier inventory; REJECTED stays with farmer
8.5. Inventory: tracks stock + reservedKg (atomic)
8.6. Orders/Payments: checkout reserves -> Razorpay create -> webhook verifies signature -> CAPTURED -> confirm order + decrement
8.7. Notifications: in-app + Socket.IO to user/procurement rooms
8.8. Market Prices: Redis cache-aside; seed history present

9. DATA CONSISTENCY & TRANSACTIONS

9.1. Boundaries
Accept-bids: transaction (create contracts, update bids, adjust awarded qty). 
Checkout reservation: transaction (lock inventory rows conceptually; update reservedKg). 
Payment confirmation: idempotent update (Payment by provider orderId/webhook event id).

9.2. Inventory
reservedKg prevents oversell. On capture -> stockKg -= qty, reservedKg -= qty. On failure paths handled.

9.3. Webhook
Verify Razorpay signature. Use idempotent keys (event_id + order_id). Never trust frontend success.

9.4. Concurrency
Prisma transactions + status checks. Avoid double-accept by status transitions.

10. SCALABILITY & PERFORMANCE

10.1. Scaling
Vertical first (single Node). Horizontal later (stateless API + LB, Redis shared, read replicas Postgres).

10.2. Caching
Redis for market prices, future: hot lists. Cache-aside pattern.

10.3. DB
Index by status/timestamps. Avoid N+1 (select with includes). Prisma query tuning.

10.4. Async
Heavy I/O (images) async. Webhooks async processing. Future: BullMQ + Redis queue.

10.5. CDN
Cloudinary CDN for images.

10.6. Bottlenecks
DB writes on hot flows (bidding bursts) -  can add queues/read replicas later.

11. RELIABILITY & FAILURE HANDLING

11.1. DB/Redis Outage
Graceful startup checks. Read-only degraded where cache missing. Critical writes fail fast with clear errors.

11.2. Payment Failures
Gateway errors -> order stays PAYMENT_PENDING. Webhook retry safe (idempotent). Never confirm without signature.

11.3. Duplicate/Delayed Webhooks
Idempotent keys prevent double processing.

11.4. Failed Deliveries
LATE -> grace -> FAILED: undelivered qty returns to procurement remaining; bidding reopens for remaining; farmer reliability decreases; original contract kept for audit.

11.5. Retries/Timeouts/Graceful Degradation
Network calls use timeouts where applicable. Socket.IO best-effort. Cache miss falls back to DB.

11.6. Backups/DR
Prod: periodic Postgres backups, Mongo backups, Redis snapshot/AOF, object store versioning.

12. SECURITY

12.1. AuthN/Z
bcrypt 10 rounds, JWT signed with secret, role guard on routes.

12.2. Headers/Rate Limit
helmet, CORS allow-list, express-rate-limit (auth strict + general).

12.3. Input Validation
Zod schemas + Multer image-only + size limit.

12.4. Payments
Server-side order + signed webhook + idempotency. Secrets in .env (never frontend).

12.5. File Uploads
Multer memory + Cloudinary upload; validate mimetype/size.

12.6. Privacy/Audit
ActivityEvent in Mongo, notifications audit. PII minimal.

14. TRADE-OFFS & DESIGN DECISIONS

| Decision                  | Options                                            | Chosen                         | Rationale | Pros | Cons | Reconsider |
|---------------------------|----------------------------------------------------|--------------------------------|---|---|---|---|
| Monolith vs Microservices | Modular monolith / Microservices                   | Modular monolith               | MVP scope, simplicity, transactions, lower ops | Fast dev, easy to reason, atomicity | Less isolated at scale | If team grows + domains decouple heavily |
| Polyglot stores           | Postgres only vs Postgres+Mongo+Redis              | Polyglot                       | Right tool: OLTP, flexible audit, cache | Clear separation | Slight complexity | Could consolidate later |
| Smart allocation          | Auto-assign vs Recommendation-only                 | Recommendation-only            | Supplier control + trust | Human-in-loop, safe | Less automated | If rules trusted + audit mature |
| Payment flow              | Front-direct vs Server+webhook                     | Server+webhook (idempotent)    | Security/compliance | Never trust frontend | Webhook handling needed | Keep |
| Inventory model           | Decrement on order vs Reserve+decrement on capture | Reserve + decrement on capture | Prevents oversell on pending payments | Correct for Razorpay flow | State complexity | Keep |
| Real-time                 | Polling vs Socket.IO                               | Socket.IO                      | Low latency for bidding | Live UX | Best-effort (not guaranteed) | Keep with DB source-of-truth |
| Bidding visibility        | Open vs Blind                                      | Open                           | Transparency | Fairness | Strategic | Can toggle per procurement |
| Ownership transfer        | On contract vs On quality verified                 | On quality verified            | Correctness | Avoids transferring bad stock | Extra step | Keep |

16. CONCLUSION

AgriConnect uses a pragmatic modular monolith with clear boundaries and correct transactional flows. 
Polyglot persistence balances consistency (Postgres) with flexibility (Mongo) and speed (Redis). 
Key strengths: transparent bidding, recommendation-only allocation, quality-driven inventory, secure server-verified payments with webhooks+idempotency. 
Current limits: single-instance MVP, optional external services, no admin panel. 
Architecture is evolvable to event-driven/microservices as scale grows.
